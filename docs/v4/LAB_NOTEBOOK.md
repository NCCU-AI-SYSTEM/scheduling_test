## 22:40　斷詞實驗（CPU）

**現象**：字元 unigram 加 bigram 的 BM25，nDCG@10 0.603，jieba 只有 0.474；加了課程詞典的 jieba 反而降到 0.452。
**解讀**

- jieba 的詞典來自簡體語料，政大課名與學生口語常被切錯。
- 字元層級不依賴詞典，學生用詞和課程文字只差一兩個字也能對上。
- 加詞典變差，可能是把課名切成長詞以後，學生只說出其中一部分（說資料分析，課名是商業資料分析）時就對不上。
**待驗證**：字元版前 10 名中沒評過分的課比例最高（26%），補評後差距可能更大。

## 22:55　文獻調查結果（agent）

**挑選要實作的方向與理由**

| 方向 | 依據 | 為什麼適合這裡 |
|---|---|---|
| 結構優先：規劃器拆條件，否定交給資料庫 | NevIR (Weller et al., 2024)、STaRK (Wu et al., 2024)、AF-Retriever (2025) | 向量模型分不清要與不要；課程資料本來就是半結構化 |
| 條件太嚴時逐步放寬 | AF-Retriever (2025) | 多條件常篩到 0 門 |
| 課程端預先生成學生問句（HyPE） | Vake et al. (2025)、Gospodinov et al. (2023) | 問句短、大綱長；成本放在離線 |
| 可吃指令的 reranker | Qwen3-Reranker (Zhang et al., 2025) | 參數量和現用的 bge-reranker 相近 |
| 評鑑面向化 | 論壇調查 | 負擔與給分佔一半的需求 |
| 修課資格用規則加 LLM | SmartCourse (Mi et al., 2025) 建議規則判斷、LLM 解釋 | 有成績單可用 |

**不做的方向與理由**

- 開放式 ReAct agent：τ-bench (Yao et al., 2024) 顯示 GPT-4o 等級的 agent 成功率不到 50%，小模型更不穩。
- 推理型檢索器（ReasonIR、Rank1）：課程查詢大多不需要深推理，8B 模型在 16GB 卡上延遲太高。

## 23:05　小模型評測結果

**解析**（185 題有效，執行結果評分）

## 23:12　修課資格：規則引擎

**結果**

- 寬鬆版（警告視為不確定）：從不誤擋（false block 0），但 84% 回答不確定，該擋的只擋到 3.9%。

**解讀**

## 23:40　Ollama 一次只載入一個模型

**現象**：HyPE（gemma4:e4b）和評鑑面向抽取（gemma4:12b）並行時，HyPE 每個請求都等到 300 秒逾時。`ollama ps` 只看到 12b。
**原因**：hopelab 的 Ollama 設定一次只保留一個模型，e4b 的請求排在 12b 後面，一直輪不到。
**處理**：停掉 HyPE，改成依序執行。順序是 GPU 佇列（面向抽取、補評）→ phase 2（修課資格、規劃器）→ phase 2.5（HyPE、補跑 CKIP 與 bge-m3 sparse）→ phase 3（端到端）。
**對部署的意義**：同一台低階主機上若同時有規劃器、面向抽取等多個模型，要嘛共用同一個模型，要嘛接受切換模型的載入時間（gemma4:26b 首次載入約 40 秒）。

## 23:45　評鑑面向抽取的中途檢查（796 組課程）

**涵蓋率**（該面向不是 null 的比例）

| 面向 | 涵蓋率 |
|---|---|
| teaching | 99.9% |
| usefulness | 95.1% |
| workload | 73.7% |
| difficulty | 69.8% |
| group_work | 38.0% |

| attendance | 21.7% |

**和大綱訊號的一致性**（Spearman）

| 比較 | ρ | n |
|---|---|---|
| 分組（評鑑）對 授課方式中小組活動比例 | 0.28 | 393 |
| 負擔（評鑑）對 報告、專題、作業、簡報佔分 | 0.17 | 448 |
| 出席（評鑑）對 出席參與佔分 | −0.08 | 128 |

**解讀**

- 期末評鑑大多在稱讚老師，很少寫給分和點名，所以這兩個面向涵蓋率低。這和資料分析看到的關鍵字比例一致：甜 0.2%、涼 0.2%、點名 0.4%。
- 一致性弱，有兩種可能：評鑑和大綱量的是不同東西（大綱寫小組活動 20%，學生不見得覺得分組多），或是 LLM 抽取本身有雜訊。
- 下一步：抽 15 組課程，由我讀原始評論後判斷抽取結果是否合理，區分這兩種原因。

## 23:55　評鑑面向人工抽查（12 組課程）

我逐則讀原始評論，判斷抽取出的分數有沒有根據（`scripts/v4/audit_aspects.py`，seed 3）。

**觀察**

- grading 的三個分數在評論裡都找不到依據，是模型自己補的。

**決策**

- 排序只採用評鑑的 workload、difficulty、group_work、teaching、usefulness。
- grading 與 attendance 不從評鑑取值；attendance 改用大綱的出席參與佔分。
- 學生問甜不甜時，系統應回答資料不足，不要推論。

**連結前一則**：出席的 Spearman 接近 0，部分原因就是抽取錯誤。這也說明涵蓋率低的面向，抽出來的值更不可靠。

## 00:20　雲端 Gemma 31B 回傳格式問題

**現象**：雲端 31B 的修課資格判斷 180 題全部解析失敗（一律記為不確定）。
**原因**：雲端模型不遵守 `format`（JSON schema），回覆外面多包一層 ```json 程式碼框；本機模型會遵守。小模型評測的解析任務本來就用 regex 取 JSON，所以沒受影響；規劃器與修課資格直接 `json.loads`，所以全部失敗。
**處理**：新增 `parse_json_object()`，取回覆中的第一個 JSON 物件；重跑雲端的修課資格與規劃。
**對部署的意義**：同一份程式切換本機與雲端模型時，不能假設結構化輸出一定被遵守，解析要有容錯。

- 指名修正讓 Precision@10 少 0.015：有指名課名時不再過濾條件，結果裡會出現不符合條件的同名課。
- 目前最好的本機設定是 gemma4:12b＋合併＋指名修正：課程單位 nDCG 0.856，MRR 0.887，規劃 0.44 秒，搜尋約 0.42 秒。

**demo 時發現並修正的兩個 bug**

1. **系所代碼對到錯的學院**：資科 703 被對成理學院。代碼表原本用全部學期多數決，但資訊學院成立前資科屬於理學院。改成只看代碼最近出現的學期，並加了回歸測試。原本的大學英文驗證用的是手寫身分，不受影響。

## 2026/11/01 22:30　評分解析器：中英對照的評分表

**現象**：五人制足球的評分寫成中文一份、英文一份（出席 50%、測驗 40%、其他 10%，接著 Attendance (50%)…），加總 200。解析器只留下兩個出席項目，測驗 40% 不見了。

**原因**：加總超過 105 時，`_collapse_children` 會把後面加起來等於前一項的項目當成子項目。測驗 40% 加其他 10% 等於第一項的 50%，就被刪掉了。

**修正**：在合併子項目之前，先檢查是不是同一份評分寫了兩種語言。判斷條件有三個：兩半的百分比序列相同、每半加總約 100、兩半的標籤是不同文字。符合時保留中文那一半。

**影響**：114-2 有 32 門課是這種寫法，保留的項目改變了 9 門。抽查都是改善，例如國際司法與國際秩序原本留下被截斷的英文標籤，現在是完整的中文標籤（期中報告或考試 30%…）。這 9 門不在 R 子集的前幾名結果裡，所以端到端分數沒有變。

**測試**：新增兩組。一組是中英對照與英文在前的寫法；另一組確認巢狀子項目和同一種語言的重複百分比不會被誤判。
