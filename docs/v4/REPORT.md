## 1. 結論摘要

評估集是 176 題從論壇真實問句改寫的題目，人工標註規劃，評審補分後已評比例 100%，見 6.4。

| 系統 | 以課程計 nDCG@10 | Success@10 | 符合硬條件的比例（Precision@10） | 指名題 MRR@10 | 一次查詢 |
|---|---|---|---|---|---|
| 線上系統複製 | 0.508 | 0.824 | 0.305 | 0.658 | 4 ms |
| 原句混合檢索＋重排（不用 LLM） | 0.724 | 0.920 | 0.488 | 0.865 | 0.47 s |
| **v4：gemma4:12b 規劃，只讀 course_struct.db** | **0.864** | **0.932** | **0.826** | **0.918** | 0.86 s |
| v4，不重排（沒有顯卡時的設定） | 0.841 | 0.943 | 0.828 | 0.903 | 搜尋約 0.1 s；CPU 上的規劃延遲未量 |
| v4，人工規劃（上限，未合併同課） | 0.896 | 0.972 | 0.966 | 0.958 | — |

主要發現：

- **最大的改進來自把條件交給資料庫**。有硬條件的題目，nDCG 從線上系統的 0.279 升到 0.757 以上，符合條件的比例從 0.305 升到 0.826。拿掉條件過濾，整體 nDCG 少 0.08，是所有元件裡最大的。
- **不用 LLM 的原句混合檢索已經拿到大部分主題分數**（主題題 0.793）。規劃器的價值在條件、指名和偏好。
- **規劃器品質是剩下的瓶頸**。人工規劃比 12b 高 0.032（以課程計；人工規劃那組沒有合併同課，合併後差距只會更大），有條件的題目差 0.12（以課號計，0.924 對 0.803）。真實問句比合成題難：e4b 的條件重疊從合成題的 0.816 掉到 0.693。
- **小模型的提示詞每多一條規則，其他欄位就可能變差**。評分方式條件寫進提示詞後，條件重疊從 0.741 掉到 0.693。封閉詞彙改用規則處理，規劃器只負責開放的部分。
- **斷詞的瓶頸在詞典**。CKIP 只比 jieba 多 0.017；不靠詞典的字元 n-gram 和 bge-m3 sparse 高出 0.15–0.19。
- **標註池偏差會選錯模型**。補評前 bge-m3 排第一，補評後落到中段，見 6.2。
- **一堂課常有多個課號**，佔全部課號的 26%。合併後前 10 名平均從 8.4 堂不同的課變成 9.1 堂，以課程計 nDCG 多 0.03。
- **修課資格要 12B 才讀得懂備註**。規則加 12b 補判，誤擋 0、該擋擋到 0.882；4B 級模型只有 0.49–0.62。
- **低階硬體**：16 GB 顯卡放得下 12B 規劃器、e5 編碼器和 0.6B reranker。沒有顯卡時，編碼器查詢要 25–126 ms，可以用；reranker 一題要 15–45 秒，不能用。不重排只少 0.023 nDCG。
- **評鑑資料談給分與點名的太少**，人工抽查發現模型會編出甜度分數，所以甜涼不從評鑑推論，見 LAB_NOTEBOOK。
- **資料問題比模型問題多**。課別代碼對錯、停開課沒排除、爬蟲把課名寫進評分欄位、中英對照的評分表被解析成兩倍，都是在逐筆對照時才發現的。

## 2. 學生怎麼問

從 PTT 選課板 149 則提問標題手動編碼，加上政大 Dcard 志願序回報串 27 篇，估計學生向選課助理提問的需求分布如下（多標籤，誤差約正負 5 個百分點）：內容主題約 30%，作業負擔約 25%，給分約 20%，老師口碑約 20%，時段、學分與通識類別、選不選得上各約 15%，修課資格約 10%。

兩個和舊做法不同的地方：

- 一半以上的問題和課程內容無關，問的是負擔、給分、老師。舊系統只索引課程內容，這些問題答不了。
- 問句很短。整理出的 248 句問句中位數 16 字；Kucia and Gawlik (2026) 在大學資訊系統上量到真實查詢平均 6.8 字。舊評估集是 LLM 讀課程大綱後寫的長句，和真實用法差很多。

一句話通常同時包含三種需求，處理方式不同：

| 需求 | 例子 | 性質 | 交給誰 |
|---|---|---|---|
| 主題 | 跟資料分析有關 | 模糊、語意 | BM25 與向量檢索、reranker |
| 硬條件 | 週三下午、英文授課、不要早八 | 精確，錯了就衝堂 | 資料庫比對 |
| 偏好 | 涼一點、不要分組、甜 | 主觀 | 評鑑與大綱的評分方式 |

### 3.2 清洗與格式化

資料分析發現的問題與處理方式：

| 問題 | 影響 | 處理 |
|---|---|---|
| 課別代碼對應錯誤：舊程式把通識對到 3、體育對到 4，實際上 3 是群修、4 是通識，體育課是 kind 1 | 學生說通識時篩出的是群修課；eval_conditions_v1 中含課別條件的題目答案錯誤 | 改用 `course_categories()`，通識看 lmtKind，體育看課名；含課別的舊題目排除 |
| 停開課 140 門沒有排除 | 推薦出不存在的課 | 載入時排除 |
| 週次進度表開頭與參考書目結尾有固定樣板文字 | 每門課的索引都帶同樣的字 | 剝除 |
| 週次主題抽取只對 23.5% 的課有效 | 主題資訊缺漏 | 改為從進度表的每個儲存格判斷，涵蓋率提升到 91.6% |
| unit 是開課班級字串（544 種），不是系所 | 系所條件比對不準 | 系所改用 subNum 前 3 碼；unit 只當開課對象 |
| 選課限制只寫在備註自由文字（845 種寫法） | 無法直接篩選 | regex 偵測類型，判斷交給規則或 LLM（見 5.4） |

可以轉成結構化欄位的資訊：

- 授課方式比例：講述、討論、小組活動、數位學習，99.9% 可解析。
- 評分方式比例：考試、報告、作業、出席等。最初的 regex 只有 60% 的課加總可靠；結構化資料庫（07_structured_data.md）改用規則加 LLM 補抽後，96.3% 的課抽得到評分項目，有百分比的課 98.5% 加總在 95–105。
- 熱門程度：選課人數除以名額。
- 歷屆評鑑：72.4% 的課連得到歷屆評論，5 則以上的有 54.5%。

### 3.3 成績單

成績單用（學年、學期、科目代碼）對回課程資料庫，59 筆全部命中。可以做的檢查：已修過、與本學期已選課程衝堂、年級限制。做不到的檢查：畢業還缺哪些必修，因為匯出檔只有學分總數，沒有系所必修科目表。

個資處理：成績單只讀主修、年級、科目代碼、及格與否，不讀姓名、學號、分數與聯絡資料（`src/v4/profile.py`）。只有學號時，學號只用來推出系所、學院、學制與年級，不保存也不輸出（`src/v4/access.py`）。

## 4. 舊做法的問題

詳見 04_prior_work_review.md，重點如下：

1. **評估集量錯了。** 每題只有一門正解，而且題目由正解課的內容生成。58% 的課有同名的其他班次，把同名班次算對以後，主題題 R@10 已達 0.979，無法分辨系統好壞。條件題合格的課中位數有 538 門，單一正解並不合理。
2. **條件塞進文字比對。** E7 在查詢後面拼接星期X、14:00 等字串給 BM25 比對，條件題只多 2 個百分點。向量模型分不清要和不要 (Weller et al., 2024)，否定條件更不能這樣處理。
3. **只做主題。** 一半以上的需求（負擔、給分、老師、資格）沒有對應的資料與流程。
4. **沒有考慮低階硬體。** 沒有比較過小模型，也沒有量過延遲。

## 5. 新方法：結構優先的課程搜尋

### 5.1 流程

```
學生的一句話（可附學號或成績單）
  │
  ▼ 規劃器（本地小模型 gemma4:12b，JSON schema 限制輸出，約 0.44 秒；最快可用 e4b，約 0.18 秒）
  │   need 主題 / named_course、named_teacher 指名 / must、must_not 硬條件 / prefs 偏好 / intents 意圖
  ├─ 評分方式條件（不要期中考、要有小考）→ 規則直接解析原句，不經規劃器
  │
  ├─ 硬條件 → 資料庫遮罩；剩不到 10 門時依可靠度逐一放寬（系所 → 課別 → 通識類別 → 學分 → 時段 → 星期 → 語言）
  │            有指名課名時不套條件過濾
  ├─ 指名老師 → 遮罩；指名課名 → 同名課排到最前
  ├─ 學號 → 學院、學制、年級；絕對選不到的課排除（學院限定、身分限定、專班…），可能選不到的加註
  ├─ 成績單 → 拿掉已修過、和已選課程衝堂的課
  ├─ 評分方式 → 大綱明確不符的排除；大綱沒寫的保留，排在明確符合的課後面
  │
  ▼ 只對主題做檢索（在遮罩內）
  │   字元 n-gram BM25 ＋ e5-large-instruct 向量 → RRF 融合前 50 名 → Qwen3-Reranker-0.6B 重排前 20 名
  │
  ▼ 偏好重排：依評鑑與大綱抽出的面向分數（負擔、難度、分組、教學、熱門程度）調整順序
  │
  ▼ 同一堂課的多個課號合併成一筆，採用最適合這位學生的課號
  │
  ▼ 前 10 堂課的結果表：課名、老師、時間、學分、課號與對象、身分加註、評分方式、授課方式、大綱連結
```

程式：`src/v4/planner.py`、`src/v4/pipeline.py`、`src/v4/catalog.py`、`src/v4/offering.py`、`src/v4/access.py`、`src/v4/assessment.py`、`src/v4/eligibility.py`、`src/v4/aspects.py`、`src/v4/present.py`。

### 5.2 每個設計的理由

| 設計 | 理由 | 依據 |
|---|---|---|
| 條件交給資料庫，不交給向量 | 向量模型分不清要與不要，否定條件尤其明顯 | NevIR (Weller et al., 2024)；ExcluIR (Zhang et al., 2025) |
| 先過濾再排序 | 先排序再過濾時，符合條件但沒進前 50 名的課永遠出不來；v1 的 post-filter 在所有題型都是淨負 | v1 實驗 E5 |
| 條件放寬 | 多條件常篩到 0 門；放寬順序依解析可靠度與學生在意程度 | AF-Retriever (2025) |
| 向量只看主題 | 原本預期星期、英文授課這些字會把向量拉向無關的課；端到端消融只差 0.001（0.823 對 0.822），條件過濾已經把這類課擋掉，所以這項設計影響很小 | 實驗見 6.4 |
| 字元 n-gram BM25 | jieba 與 CKIP 都靠詞典，政大課名與大綱的專有名詞常切錯；字元層級補評後 nDCG 0.666，jieba 0.500、CKIP 0.517 | 實驗見 6.2 |
| 規劃器用 gemma4:12b | 真實問句上本機最準，16 GB 顯卡放得下規劃器、編碼器和重排；e4b 在合成題最好、速度最快 | 實驗見 6.1、6.4 |
| 編碼器用 e5-large-instruct | 補評後 0.834，接近 Qwen3-Embedding-4B 的 0.845，延遲只有它的 27% | 實驗見 6.2 |
| 同一堂課合併 | 26% 的課號和別的課號是同一堂課，不合併時前 10 名平均只有 8.4 堂不同的課 | 實驗見 6.4 |
| 評分方式用規則解析 | 寫進規劃器提示詞會讓條件重疊從 0.741 掉到 0.693；評分方式的說法是封閉詞彙 | LAB_NOTEBOOK 2026/10/19 10:00 |
| 身分篩選只排除絕對選不到的課 | 加簽可以讓限本系等限制例外，使用者確認只排除學院、身分、專班、學制這類 | LAB_NOTEBOOK 2026/10/19 08:30 |
| Qwen3-Reranker-0.6B | 比 bge-reranker-v2-m3 高約 1 個百分點；4B 版再高 1.4 個百分點但慢 4 倍 | 實驗見 6.3 |
| 偏好只用可信的面向 | 人工抽查發現評鑑幾乎不談給分，模型會編出甜度分數 | LAB_NOTEBOOK 23:55 |
| 修課資格：規則擋明確的，其餘交給 LLM 或標警告 | regex 能偵測限制，但判斷不了學生是否符合 | 實驗見 6.5 |
| 固定流程，不用開放式 agent | 小模型的多步工具呼叫不穩定，延遲難控制 | τ-bench (Yao et al., 2024) |

## 6. 實驗結果

### 6.1 小模型的理解與工具使用

條件一致：同一份提示詞、溫度 0、關閉 thinking、一次一個請求。在 hopelab 本機跑；雲端 Gemma 31B 跑在 Ollama 的伺服器，延遲不代表本機。

**解析硬條件**

185 題有效題目（含課別條件的 35 題因答案錯誤而排除），用執行結果評分：

- 保留正解：正解課是否還在解析出的條件篩選結果裡。
- 篩選重疊：解析條件篩出的課，和標準答案篩出的課的 Jaccard。

| 模型 | 保留正解 | 篩選重疊 | 否定題重疊 | 中位延遲 | 備註 |
|---|---|---|---|---|---|
| gemma4:e4b | 0.886 | **0.816** | **0.784** | **0.10 s** | 全在 GPU |
| gemma4:12b | 0.870 | 0.790 | 0.721 | 0.32 s | |
| gemma4:31b（雲端） | 0.886 | 0.790 | 0.783 | 0.62 s | p95 6.25 s，受速率限制 |
| qwen3.8:27b | **0.924** | 0.774 | 0.718 | 1.29 s | 27% 跑在 CPU |
| qwen3.6:35b-a3b | 0.897 | 0.763 | 0.682 | 0.64 s | MoE，部分在 CPU |
| gemma4:26b | 0.941 | 0.752 | 0.641 | 0.42 s | MoE，常漏抽條件，所以保留正解高、重疊低 |
| qwen3.5:9b | 0.865 | 0.723 | 0.637 | 0.42 s | |
| qwen3:8b | 0.800 | 0.721 | 0.639 | 0.19 s | |
| qwen3.5:4b | 0.784 | 0.712 | 0.659 | 0.30 s | |
| gemma4:e2b | 0.838 | 0.603 | 0.537 | 0.09 s | |
| qwen3.5:2b | 0.692 | 0.518 | 0.372 | 0.21 s | |
| qwen3.5:0.8b | 0.741 | 0.333 | 0.287 | 0.10 s | 幾乎不抽條件 |

觀察：

- 4B 以上的模型篩選重疊都在 0.7 以上，2B 以下明顯掉到 0.6 以下，否定題掉得更多。
- 模型越大不一定越好：gemma4:e4b 勝過 26B 與 27B。大模型傾向少抽條件，所以保留正解的比例高，但篩不準。
- 這組題目是從課程欄位生成後由 LLM 改寫的，句型偏工整，比真實問句好解析。真實問句的解析表現見 6.4。

觀察：

- gemma4:e4b／e2b 在原始提示詞下大多不呼叫工具，改成反問學生想要什麼時段、什麼學分。加一句提示後，e4b 從 0.30 升到 0.83。
- Qwen 3.5 4B／9B 兩種提示詞都穩定，對提示詞比較不敏感。
- 0.8B 會在想學日文時設定授課語言為日文（禁止參數比例 17%），2B 以上大多不會。

**小模型的限制整理**

- 理解：2B 以下的模型常漏掉否定，也分不清想學日文和日文授課。
- 工具：能力差異不大，行為差異很大；Gemma 小模型傾向反問，要靠提示詞約束。
- 效率：超過 16GB 的模型（26B 以上）部分跑在 CPU，延遲多 3–10 倍。雲端 31B 準確但有速率限制，8 個並發就回 429。

### 6.2 檢索元件：斷詞、sparse、dense

**題目**：v3 評估集 418 題，分兩組。

- T 組 240 題，原句直接搜尋，口語與主題各半。
- M 組 178 題，帶條件，先用標準答案的條件過濾，只比主題檢索。這樣條件解析的錯誤不會算到編碼器頭上。

**評分**：nDCG@10，分補評前與補評後兩欄。

- **斷詞準不準不是瓶頸，詞典才是**。CKIP 是繁體中文專用的斷詞器，補評後只比 jieba 多 0.017；加政大詞典的 jieba 反而更差。不靠詞典的方法，字元 n-gram（0.666）和 bge-m3 sparse（0.687），補評後比 jieba 和 CKIP 高 0.15–0.19。課名和大綱裡的專有名詞，例如課程代號、外語詞、新領域名稱，大多不在詞典裡。
- bge-m3 sparse 比字元 n-gram 高 0.021，但每份文件都要過一次 GPU 編碼。流程用字元 n-gram，因為 sparse 的角色是補精確字串，dense 已經負責語意。
- **補評改變了排名**。補評前 bge-m3 第一（0.796），補評後落到中段（0.800），e5-large-instruct 從 0.762 升到 0.834。原因是標註池偏差：v3 的標註池是用 bge-m3 系統的候選做的，所以 bge-m3 的前 10 名有 97% 已經標過，其他編碼器只有 79–83%。沒標過的課在補評前一律算不相關，等於懲罰和 bge-m3 找法不同的模型。只看補評前的分數會選錯模型。
- **選 e5-large-instruct**：補評後只比 Qwen3-Embedding-4B 低 0.011，延遲只有它的 27%。
- **這個選擇在端到端沒有得到確認**。換回 bge-m3 的端到端 nDCG 是 0.829，e5 是 0.823（見 6.4 消融），兩者差不多，bge-m3 還略高。元件評估用的 v3 題目帶有合成偏差，04_prior_work_review.md 測過它和課程文字的 bigram 重疊偏高；端到端用的是真實口吻問句，在完整流程裡，兩個編碼器的差距被條件過濾和重排吸收。結論是兩者都可以用，選哪個要看 CPU 上的成本，見 6.6。
- **RRF 融合在這裡沒有幫助**。字元 BM25 和 bge-m3 融合後 0.779，比 bge-m3 單獨還低；字元 BM25 的分數低太多，融合時是把 dense 往下拉。端到端流程仍然保留 BM25，因為它在指名課名、課程代號這類精確字串上比較可靠，見 6.4 的消融。

**觀察**

- 在這組題目上，重排是單一元件中增益最大的：RRF 從 0.779 升到 0.850，多 0.071。
- Qwen3-Reranker-0.6B 比 bge-reranker 高 0.015，延遲多 84 ms。4B 版再高 0.013，延遲是 0.6B 的 4 倍，所以選 0.6B。

- **實作上的記憶體問題**：Qwen3-Reranker 是生成式模型，原本會對每個位置都算 15 萬詞的 logits，在規劃器 12B 同時載入時會超出 16 GB。改成只算最後一個位置（`logits_to_keep=1`），分數不變，記憶體問題消失。

- **和線上系統比**，以課號計的 nDCG 從 0.528 升到 0.823（e4b）或 0.855（12b）。差距大多在有條件的題目：0.279 升到 0.757，硬條件命中率從 0.305 升到 0.784。條件改由資料庫判定，是最大的一項改進。
- **不用 LLM 也能拿到大部分主題分數**。原句混合檢索的主題題已有 0.793，v4 只多 0.087。規劃器的價值在條件與偏好。

- **合併同課**讓以課程計的 nDCG 多 0.03，前 10 名平均多出 0.7 堂不同的課。以課號計的分數下降是指標本身的問題：理想排序裡有重複課號，合併後的系統不可能排出來。

### 6.5 修課資格

  - 學號就能推出學院、學制與年級，不需要成績單。
  - 實測大學英文（二）56 班：資科學三只看到自己學院的 9 班，全部在週三 D56。
  - 依使用者確認的規則，限本系和非灌檔對象的必修灌檔課都是顯示加註，不排除。

### 6.6 沒有顯卡時的成本

前面的延遲都是在 RTX 5080 上量的。為了檢查低階硬體能不能跑，把編碼器和 reranker 改在 CPU 上執行：
- 硬體：hopelab 的 Ryzen 9 9900X，12 核。另外限制成 4 執行緒，模擬一般筆電。
- 每個模型各開一個行程，所以記憶體是單一模型的峰值。
- 建索引時間：用 200 份課程文件實測，再推算到全部 2,655 門。
- 程式：`scripts/v4/cpu_bench.py`，結果在 `results/v4/cpu_bench.json`。

**編碼器**

| 模型 | 補評後 nDCG（6.2） | 查詢延遲 12 執行緒 | 查詢延遲 4 執行緒 | 建索引 12 執行緒 | 建索引 4 執行緒 | 記憶體 |
|---|---|---|---|---|---|---|
| bge-base-zh-v1.5 | 0.792 | 14 ms | 25 ms | 3.7 分 | 10.8 分 | 1.8 GB |
| e5-large-instruct | 0.834 | 43 ms | 79 ms | 12.3 分 | 35.4 分 | 4.1 GB |
| bge-m3 | 0.800 | 57 ms | 55 ms | 14.2 分 | 41.9 分 | 3.1 GB |
| Qwen3-Embedding-0.6B | 0.804 | 86 ms | 126 ms | 31.9 分 | 76.2 分 | 7.0 GB |

**Reranker**：重排一題的前 20 門課。

| 模型 | 12 執行緒 | 4 執行緒 | 記憶體 | GPU 上（6.3） |
|---|---|---|---|---|
| bge-reranker-v2-m3 | 15.8 s | 44.5 s | 3.3 GB | 121 ms |
| Qwen3-Reranker-0.6B | 15.1 s | 37.9 s | 6.2 GB | 205 ms |

**觀察**
- **編碼器在 CPU 上可以用**。查詢只要編碼一句短話，最慢的 Qwen3-Embedding-0.6B 也只要 126 ms。建索引比較久，但每學期只要離線跑一次，課程資料更新時再補算有變的課即可。
- **Reranker 在 CPU 上不能即時使用**。一題要 15–45 秒，比 GPU 慢 75–200 倍。原因是每門課要和問句一起讀，最多 1,536 個 token，20 門課合計約 2 萬個 token。6.4 的消融顯示，重排在完整流程裡只多 0.011 nDCG，所以沒有顯卡就直接關掉重排，搜尋延遲是編碼器加 BM25，約 60–90 ms。
- **沒有顯卡時建議用 e5-large-instruct**。它在 4 執行緒的查詢延遲（79 ms）只比 bge-m3（55 ms）多 24 ms，補評後的分數較高；端到端兩者差不多（6.4）。記憶體只有 2 GB 的機器才考慮 bge-base-zh，它的補評分數低 0.042。
- **沒試的加速方法**：把 reranker 的輸入截到 512 token、只重排前 10 門，或用 ONNX int8 量化。依 token 數估計，前兩項合起來大約能把時間降到原本的 1/6，CPU 上仍要好幾秒，所以沒有實作。
- **規劃器的 CPU 延遲還沒量**。規劃器跑在 Ollama 上，量測要和結構化資料的批次工作搶 Ollama，排在那之後。

## 7. 建議與下一步

### 7.1 部署設定

| 元件 | 有 16 GB 顯卡 | 只有 CPU | 依據 |
|---|---|---|---|
| 資料 | `course_struct.db` 一個檔，39.4 MB | 同左 | 6.4、07_structured_data.md |
| 規劃器 | gemma4:12b（本機 Ollama） | gemma4:e4b，延遲待量 | 6.1、6.4 |
| 評分方式條件 | 規則解析原句 | 同左 | LAB_NOTEBOOK 2026/10/19 10:00 |
| 編碼器 | e5-large-instruct | e5-large-instruct，4 執行緒查詢 79 ms | 6.2、6.6 |
| 重排 | Qwen3-Reranker-0.6B，前 20 名 | 關掉 | 6.3、6.6 |
| 修課資格 | 學號推身分，加規則，再由 12b 補判 | 學號與規則；LLM 補判改成只顯示警告 | 6.5 |
| 雲端 | gemma4:31b 只當選配，8 個並發就回 429，要保留本機備援 | 同左 | 6.1 |

**更新流程**（每學期）：
1. 爬蟲更新 1142.db。
2. 執行 `python -m scripts.v4.build_structured`。
3. 執行 `python -m scripts.v4.build_runtime --encoder e5-large-instruct --aspects <面向檔>`。
4. 用 `python -m scripts.v4.verify_structured` 檢查覆蓋率。
5. 換上新的 course_struct.db。

LLM 補抽的結果依輸入文字快取，同一份大綱不會重複呼叫模型。

### 7.2 移植到線上系統的順序

依增益和改動大小排序：

1. **course_struct.db 加上條件過濾**：線上系統最大的落差在有條件的題目，0.279 對 0.757 以上。只需要規劃器輸出條件，再用資料庫篩選；檢索可以先沿用線上的。
2. **規劃器與指名比對**：課名、老師精確比對，加上縮寫展開。指名題 MRR 從 0.658 升到 0.918。
3. **同課合併與學號身分篩選**：結果表依課程顯示，排除選不到的課。
4. **字元 n-gram BM25 取代 ParadeDB 的 jieba**，編碼器換成 e5-large-instruct。
5. **偏好重排與評分方式條件**。
6. **有顯卡的話再加重排**。

### 7.3 下一步研究
