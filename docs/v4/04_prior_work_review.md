# 既有實驗與程式的批判性檢視

檢視範圍：scheduling_test 的 v1 實驗（2026/04–05）、v3 評估（2026/10/05）、CourseLangChain `origin/feat/mcp-test` 的線上檢索、CourseDataPrep 的資料準備。結論分成三類：可以沿用、要修正後沿用、不可信。

## 1. v1 實驗（E0–E7）

v1 的主軸是把課程內容放進索引，再疊上 BM25、bge-m3、RRF 和 reranker。從現行系統 R@10 0.288 做到 E7 的 0.768。方向沒有問題，但數字的可信度有四個問題。

**評估集是從正解生成的。** eval_synth 的 8,253 題都由 gpt-4o-mini 讀一門課的內容後寫出問句，每題只有那一門課算對。114-2 有 58% 的課有同名的其他班次，系統推了同一門課的另一班會被算錯。把同名班次算對以後，主題題 R@10 是 0.979，口語題 0.940，已經沒有區分能力。條件題（例如週三下午中文授課）合格的課中位數有 538 門，用單一正解衡量並不合理。Rahmani et al. (2024) 指出，只把來源文件當正解時，合成題目與真實題目的系統排名一致性從 τ=0.82 掉到 0.16。

**生成器重疊。** 評估題目和 D-V2 的課程摘要大多出自 gpt-4o-mini。我量了主題與口語題的字面重疊：查詢的雙字詞有 31.6–34.5% 出現在該課的 LLM 摘要與關鍵字裡，出現在課名加課程目標的是 26.0–27.9%（`scripts/v4/check_synth_leakage.py`）。差距不大，但 D-V2 讓 BM25 從 0.328 升到 0.444，這段增益有多少來自兩邊用同一個模型的用詞習慣，目前無法和真實收益分開。

**樣本混用、沒有檢定。** 部分設定只跑 500 題子集，部分跑全 8,253 題，表格放在一起比較。E7 比 E3 高 0.2 個百分點就被記為新最佳，沒有信賴區間或 paired test。

**HyDE 與 Q2D 的否定結論不穩。** 這兩個方法是讓 LLM 先把短問句擴寫成像文件的文字再檢索。合成題目本來就長得像課程描述，擴寫幫不上忙；真實學生的短句（想學 ML）情況可能不同。在有真實問句之前，這個結論只能算暫定。

可以沿用的部分：文件加入課程目標的收益很大（Dense 0.549 → 0.675），在任何評估設計下都應該成立；reranker 取前 20 優於取前 50；post-filter 會誤殺主題題，這個機制上的觀察也成立。

## 2. 條件解析（P0–P3）

- eval_conditions_v1 的 2,160 題是先從正解課的欄位抽條件，再請 LLM 改寫成句子。句型偏工整，比真實問句好解析。
- 指標用字串比對的 slot F1。系所欄位實際上是開課班級字串（例如法律碩一法律博一法律碩二法律博二），模型輸出法律就會被判錯，所以系所 F1 0.893 低估了實際效果。
- Oracle filter 保留正解 99.86% 是必然結果，因為條件本來就是從正解課抽出來的。它只能證明過濾邏輯沒寫錯，不能證明條件過濾有效。
- 只測了雲端大模型（gpt-4.1-mini、claude、gemma-4-31b），沒有測可以在低階硬體上跑的小模型。

v4 改成用執行結果評分：把解析出的條件丟進資料庫，看正解課是否被保留、篩出的課和標準答案的重疊（Jaccard）多少（`scripts/v4/llm_bench.py`）。

## 3. v3 評估（2026/10/05）

v3 修掉了單一正解的問題：從多個系統的前 20 名合起來，由 qwen3:14b 依 UMBRELA (Upadhyay et al., 2024) 的 0–3 分給主題分，條件是否滿足交給資料庫判定，兩者相乘。仍有以下限制：

- 評審只有一個模型，人工校準沒有做，κ 未知。評審給分偏寬：20,623 對裡 55% 被評 2 分以上。
- 主題題與混合題仍是 eval_synth 的合成題，只是換了評分方式。
- Pooling 用的系統全都以 bge-m3 為核心，換成其他 embedding 的系統會撈到沒評過的課。補評機制（`scripts/rescore_v3.py`）可以緩解。
- M 子集丟掉了正解課不滿足的條件（200 題丟了 60 個，其中系所 49 個），子集因此變得比較容易。

結果仍有參考價值：在 740 題上，線上系統複製版 nDCG@10 0.454，E7 0.735，E7 加 LLM 條件解析 0.827，條件全對的上限 0.908。

## 4. 線上系統（CourseLangChain feat/mcp-test，2026/09/26）

- 架構是 brain agent 加工具，檢索在 `tools/retrieve.py`：ParadeDB 的 jieba BM25 加 pgvector 逐欄分塊（bge-base-zh-v1.5），在 SQL 裡做 RRF，沒有 reranker。
- 條件只有 `text_to_sql_tool` 處理時間，其他條件（語言、課別、系所、通識類別）沒有結構化處理。
- 課程資料準備在另一個 repo CourseDataPrep，目標學期 115-1，但 NCCUCourse 本地沒有 1151.db。
- 部署 repo CourseLangChain-all 的 submodule 停在 2026/03–04 的舊版本，course.andyjjrt.cc 查不到網域。

## 5. 整體缺口

1. 沒有真實學生問句，所有評估都靠 LLM 合成。
2. 沒有修課資格判斷。全人匯出的修課紀錄沒有被使用。
3. 沒有使用學生評鑑（26.9 萬則）、選課結果、歷屆課程，答不了好過嗎、選得上嗎、作業多嗎這類最常見的問題。
4. 沒有在低階硬體上量過延遲，也沒有比較小模型。
5. 方法上停留在 2023 年左右的 RAG 標準組合（BM25、dense、RRF、cross-encoder）。條件處理靠在查詢後面拼接星期X、14:00 這類字串，把結構化資訊塞進文字比對，效果有限（條件題只多 2 個百分點）。
